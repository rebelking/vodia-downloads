# Vodia MCP 0.13.1

Vodia MCP 0.13.1 corrects the guarded phone-provisioning helper to match the
request generated by the Vodia administration UI.

## Corrected provisioning request

`plan_provision_mac` now plans this operation:

```text
POST /rest/system/prov_phones
```

The immutable request body uses the verified UI fields:

```json
{
  "mac": "0C383E15C577",
  "pin": "",
  "vendor": "Fanvil",
  "model": "V64",
  "ip": "",
  "extension": "2003",
  "name": "Fanvil",
  "siptrans": "",
  "prov_t38": "",
  "domain": "vodiatech.audiomercy.com"
}
```

The helper no longer posts this workflow to `/rest/domain/{domain}/macs`. It
uses singular `extension` and does not send `refresh`, `template`, or plural
`extensions` fields.

## Fanvil and Yealink requirements

- Fanvil phones do not require a serial ID.
- Vendor/model values are canonicalized from the live PBX catalog, preserving
  exact values such as `Fanvil` and `V64`.
- Yealink continues to require the full serial number, mapped internally to the
  legacy `pin` wire field and redacted from previews and audit output.
- Empty `pin`, `ip`, `siptrans`, and `prov_t38` values are sent when no override
  is supplied, matching the verified Vodia UI request.

## Safety

Planning remains read-only. Applying still requires the separate
`apply_vodia_change` call with the exact confirmation string. Before applying,
the connector re-reads `/rest/system/prov_phones` and rejects the plan if the
target phone changed. It then performs a targeted verification read.

Automated tests cover the exact Fanvil V64 payload, case canonicalization,
required MAC/extension/domain fields, planning without writes, Yealink serial
handling, and the absence of unsupported fields.
